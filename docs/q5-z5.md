Real mode — seeds are computed from trigonometry (solve(pgon, "a", 4, "r") etc.), giving true irrational

 (.vr, .neg, .hr).

 goThick()/goThin() — the same wheel math but on the integer grid.

Mosaic mode — same integer seeds as Quadrille but uses shapeWheelMosaic() which applies mosaic-specific reflections
(.vrm, .negm, .hrm).

The wheel recursion is identical across all modes — same makeWheels(), same Wheel class. The only difference is:

1. The seed points (irrational vs integer)
2. The shape functions that extract rhomb vertex positions from wheel data (goThickReal vs goThick)
3. The reflection operators for shape wheels

So the tile placement math (where children go) is mode-independent — it's the shape geometry (what gets drawn at
each position) that differs.

## Motivation

Real mode coordinates are floating-point approximations of values that live
exactly in Q(√5) — the rationals extended by √5. This causes:

- Floating-point comparison failures (critical for edge hash table in dihedral
  stroke plan)
- Drift at deep recursion levels
- No clean unification with the integer-based mosaic/quadrille modes

## The Idea

Replace `Point(x: number, y: number)` with exact coordinates where each
component is `a + b√5` stored as a pair `(a, b)`. With the right scaling, all
values can live in Z[√5] (integer a, b) — no fractions needed.

## Current Architecture

### Real mode seeds (shape-modes.js, Real constructor)

The trig constants are all in Q(√5):

```
c_0 = 1
c_1 = (√5 - 1) / 4        → needs ×4 to clear denominator
c_2 = (√5 + 1) / 4        → needs ×4
s_1 = √(10 + 2√5) / 4     → involves nested radical
s_2 = √(10 - 2√5) / 4     → involves nested radical
```

The nested radicals `√(10 ± 2√5)` are the complication. These are NOT in Q(√5)
directly — they involve `√(a + b√5)` which is a degree-4 algebraic number.
However, `sin` and `cos` of multiples of 36° can be expressed in Q(√5) when
squared, and the products that appear in the wheel coordinates may simplify.

### Seed magnitudes

Seeds are built by scaling unit direction vectors by magnitudes derived from
pentagon/pentagram geometry:

```
pMag = 2 * pgon.r    (with a=4)    ≈ 5.506
sMag = pgon.R + pgram.R             ≈ 4.217
tMag = 2 * (pgram.R + pgram.y)     ≈ ...
dMag = pgon.r                      ≈ 2.753
```

The pgon/pgram properties (R, r, x, y, rho) all involve √5 and nested radicals.

### Quadrille seeds (integer approximations)

```
pSeed = [p(0, -6), p(3, -4), p(5, -2)]
sSeed = [p(0, -5), p(3, -5), p(5, -1)]
tSeed = [p(0, -8), p(5, -8), p(8, -2)]
dSeed = [p(0, -3), p(2, -3), p(3, -1)]
```

These are hand-tuned integer points that approximate the real geometry on a
grid. The real seeds scaled by some factor should land near these integers.

### The multiplier question

The real seeds appear to be scaled so that their coordinates land near the
quadrille integers. The comment in `goThickReal` (line 134) notes:

> "Can this be unified with quad and mosaic. The only difference is the line
> in the rh routine d + p == t."

In quadrille: `p + d ≠ t` exactly (p(0,-6)+p(0,-3) = p(0,-9) ≠ p(0,-8)),
but in real mode `t` is constructed from different geometry (star feet distance)
so `p + d` might equal `t` there. If so, the goThick/goThickReal split could
be eliminated.

Investigation needed: what multiplier (5? 10? 4?) applied to the real
unit-circle coordinates produces values closest to the quadrille integers?
This would reveal the intended scaling relationship.

## Proposed Q5 Number Type

```js
class Q5 {
    constructor(a, b) {
        this.a = a; // rational part
        this.b = b; // √5 coefficient
    }
    add(other) {
        return new Q5(this.a + other.a, this.b + other.b);
    }
    neg() {
        return new Q5(-this.a, -this.b);
    }
    sub(other) {
        return new Q5(this.a - other.a, this.b - other.b);
    }
    mul(other) {
        return new Q5(
            this.a * other.a + 5 * this.b * other.b,
            this.a * other.b + this.b * other.a,
        );
    }
    scale(k) {
        return new Q5(this.a * k, this.b * k);
    }
    toFloat() {
        return this.a + this.b * Math.sqrt(5);
    }
    equals(other) {
        return this.a === other.a && this.b === other.b;
    }
    toString() {
        return `${this.a}+${this.b}√5`;
    }
}
```

1 = Q5(1, 0)

## Proposed Q5 Point Type

```js
class Q5Point {
    constructor(x, y) {
        this.x = x; // Q5
        this.y = y; // Q5
    }
    tr(v) {
        return new Q5Point(this.x.add(v.x), this.y.add(v.y));
    }
    get vr() {
        return new Q5Point(this.x, this.y.neg());
    }
    get hr() {
        return new Q5Point(this.x.neg(), this.y);
    }
    get neg() {
        return new Q5Point(this.x.neg(), this.y.neg());
    }
    mult(m) {
        return new Q5Point(this.x.mul(m), this.y.mul(m));
    }

    // For rendering — evaluate to float
    toPoint() {
        return new Point(this.x.toFloat(), this.y.toFloat());
    }

    // For edge hashing — exact string key
    get key() {
        return `${this.x.a},${this.x.b}|${this.y.a},${this.y.b}`;
    }
}
```

## The Nested Radical Problem

The sin/cos values at 36° increments involve `√(10 ± 2√5)`, which is NOT in
Q(√5). However:

- `sin²(36°) = (10 - 2√5) / 16` — this IS in Q(√5)
- `cos²(36°) = (6 + 2√5) / 16` — this IS in Q(√5)

So squared distances and dot products work in Q(√5), but actual coordinates
require `√(a + b√5)`, which lives in Q(√5, √(something)) — a degree-4 field.

**Possible workarounds:**

1. Work with a 4-component representation: `a + b√5 + c·sin36° + d·cos36°`
   (essentially Q(√5, sin36°))
2. Scale everything so coordinates are products of sin/cos with Q(√5) magnitudes
   — the products may simplify to Q(√5)
3. Use the wheel recurrence (which only involves addition of existing points)
   as the basis — if the GEN-0 seeds can be expressed exactly, all higher gens
   are exact via addition

**Option 3 is promising:** the wheel `makeWheels()` function only uses `tr()`
(addition). If we can express the base seeds exactly in some number system, all
derived wheels are exact by construction. The seeds are `unitDirection × magnitude`,
and the product `sin(k·36°) × magnitude` might simplify.
